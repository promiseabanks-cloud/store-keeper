# Decisions log

Every deviation from the brief (§ references are to `docs/BRIEF.md`) and every choice made where the brief was silent is recorded here with its reason.

| # | Date | Area | Decision | Reason |
|---|---|---|---|---|
| D-001 | 2026-11-15 | Naming | Working product name is **Store Keeper**. PHP namespace `StoreKeeper\Commerce` / `StoreKeeper\Platform`, table prefix `storekeeper_`, REST namespace `storekeeper/v1`, hook prefix `storekeeper/`, option prefix `storekeeper_`, capability prefix `storekeeper_`, text domain `storekeeper`, all read from `Core/Brand.php`. | §7.2 requires every name to come from one constants file. PHP namespaces cannot be dynamic, so the namespace itself is the one name that is fixed in code; renaming is a mechanical find/replace plus the `Brand` constants. |
| D-002 | 2026-11-15 | Engine ↔ WordPress coupling | The engine talks to the database through a narrow `Core\Database\Connection` interface with two implementations: `WpdbConnection` (production, wraps `$wpdb`) and `PdoConnection` (tests, CLI, WP-CLI tooling). | §6.1 requires the engine to be free of HTTP/HTML knowledge so it can be tested directly. A narrow interface keeps every production call on `$wpdb->prepare()` (§19.1) while allowing the engine test suite in §21.1–21.2 to run without a full WordPress install. |
| D-003 | 2026-11-15 | Schema bookkeeping | Applied migrations are tracked in a `{p}schema_migrations` table (and `{n}schema_migrations` at network level) rather than an option. | Migrations must run identically under WordPress and under the PDO test driver; a table works in both, and a network upgrade can then verify both prefixes in one query. §8 allows adding tables. |
| D-004 | 2026-11-15 | Test database | Integration/concurrency tests run against real MariaDB (MySQL-compatible), never SQLite. | §6.2 requires InnoDB transactions and row locking; §9.4 relies on conditional `UPDATE` semantics and §21.2 on real parallel connections. SQLite would not prove either. |
| D-005 | 2026-11-15 | Reservation location split | v1 reserves each order line from a single location: the first sellable location (by `online_priority`) with enough available stock. The `InventoryService::reserve()` signature already accepts a location, and `OrderService` selects it, so splitting across locations later is a service change only. | §9.4 explicitly permits this simplification for the pilot while keeping the interface ready. |
| D-006 | 2026-11-15 | Ledger writes | `InventoryService` performs every movement as: ensure `stock_levels` row → lock it (`SELECT … FOR UPDATE`) → mutual-exclusion check or conditional `UPDATE` → insert append-only movement → update `last_movement_id`. All inside one transaction; hooks fire after commit. | §9.3. Locking first is what makes the `reserved <= on_hand` invariant hold under the concurrency test (§21.2), and the movement insert stays in the same transaction as the level change. |
| D-007 | 2026-11-15 | Hooks | Engine events go through `Core\Hooks\Hooks` (`InMemoryHooks` for tests, `WpHooks` in production calling `do_action`). | §6.1 and §12.6 require hooks at every state change, and tests must be able to assert they fired after commit. |
| D-008 | 2026-11-15 | Money rounding | Percentage arithmetic (fees, discounts) rounds half up to the kobo in integer space: `intdiv(amount * basisPoints + 5000, 10000)` for non-negative amounts, symmetric for negatives. | §19.2 requires one documented rounding rule and no float arithmetic. |
| D-009 | 2026-11-15 | Idempotency storage | `IdempotencyService` stores `(scope, actor_key, idem_key) → request_hash + response` in `{p}idempotency_keys`, and returns the stored response for an identical retry, `DuplicateRequest` (HTTP 409) for a different body. | §8.5 and §18. The table already models exactly this; the service is transport-agnostic so REST middleware and POS sync share it. |
| D-010 | 2026-11-15 | Auditor | Audit writes are an interface (`Audit\AuditLogger`), with the database implementation used by services; actor context (`staff`, `owner_impersonation`, `system`, `device`, `customer`) is passed explicitly, never read from globals. | §5.2 and §19 require audit entries for sensitive actions, and impersonation must be distinguishable from real staff actions. |
| D-012 | 2026-11-15 | Ledger locking | Every stock mutation first takes the `stock_levels` row lock (`SELECT … FOR UPDATE`), then inserts its movement and applies the delta; batches lock variants in ascending id order. | The first concurrency run produced deadlocks because `INSERT IGNORE` on an existing level took a shared lock that was then upgraded to exclusive. Locking first makes the 50-buyer test deterministic; the conditional `UPDATE` remains as a second guard (§9.4). |
| D-013 | 2026-11-15 | Phase 1 REST scope | Phase 1 ships the REST conventions (capability auth helper, idempotent write helper, error mapper, no-store headers) and registers routes with their screens in later phases. | §22.2 asks for a REST *skeleton* in this phase; §18 requires each endpoint to be documented as it ships, so routes are added with the UI that exercises them. `docs/API.md` records the status of each area. |
| D-014 | 2026-11-15 | Third payment gateway | The third gateway (brief §1.5 "GoPay") is **OPay**. Added `opay` to the `payments.method` enum in migration `0006_payments_opay` and kept `gateway3` so no existing row can break. The OPay adapter implements the shared `GatewayAdapter` in Phase 3 alongside Paystack and Flutterwave. | Owner confirmed the provider. §13.2 requires one adapter per provider, never provider-specific logic in services. |
| D-015 | 2026-11-15 | Gateway credentials | Each store's gateway configuration is one option (`storekeeper_payment_gateways`) keyed by slug (`opay`, `paystack`, `flutterwave`). Public keys and flags are plain; secret keys are encrypted with `sodium_crypto_secretbox` under a key derived from `WSP_ENCRYPTION_KEY` (`Core\Crypto`) and only a last-4 hint is ever returned. A blank secret on save keeps the stored value. | §19.4 requires secrets encrypted at rest with a key outside the database, and a merchant must be able to rotate a public key without re-typing the secret. Options are already per-site, so the tenant boundary stays obvious. Losing the constant makes secrets unrecoverable; the mu-loader warns when it is missing. |
| D-016 | 2026-11-15 | Gateway amounts | The adapter interface takes and returns integer kobo (`amount_kobo`, `fee_kobo`) and plain array results instead of the brief's `Money`, `InitializeResult` and `VerifyResult` value objects. | Every other engine service already passes kobo as an integer, and `Core\Money` exists only for pricing arithmetic. Arrays keep the REST layer a direct serialisation of a verification, which is also what gets stored in `payments.gateway_payload` for audit. The interface methods and adapter-per-provider boundary of §13.2 are unchanged. |
| D-017 | 2026-11-15 | Flutterwave webhook | Flutterwave's `verif-hash` is checked against the store's stored secret key, so the merchant sets their Flutterwave secret hash to the same value as their secret key in the Payment gateways screen. | `GatewaySettings` stores one secret per gateway (§19.4, D-015). Adding a second secret field for one provider would complicate the screen and let the two drift apart; the secret key is already private, so using it as the hash loses nothing. |
| D-018 | 2026-11-15 | OPay webhook signature | An OPay callback is accepted if its signature matches HMAC-SHA512(body), HMAC-SHA3-512(body), or HMAC-SHA512(requestTimestamp . body) with the store's secret key. Accepted callbacks only trigger a status query. | OPay's documentation shows SHA-512 and SHA3-512 for callbacks, and a v2 header that signs the timestamp with the body. The signature is not the trust boundary for money — `cashier/status` is — so accepting every documented shape costs nothing and avoids silently dropping real callbacks after a provider change. |
| D-019 | 2026-11-15 | Phase 3 adapter surface | `GatewayAdapter` ships checkout, server-side verify, fee calculation and webhook verification. Virtual accounts, refunds and the recurring reconciliation job are deferred; `supports('virtual_account')` and `supports('refund')` answer false for every adapter. | §22.3 gates Phase 3 on the gateway interface and the payment path, not on every payment feature. Virtual accounts need per-customer account creation and a settings choice; refunds need the refunds screen and stock restocking rules (§12.4). Shipping a half-wired refund that moves no stock would be worse than an honest false. |
| D-020 | 2026-11-15 | Phase order | The build finished the outstanding back-office items from §22.3 (customers, approvals, prices, locations, staff, alerts) before starting the storefront that §22.5 calls Phase 4. | The brief's own phase gate for the back office is "a pilot merchant can load their real catalog and run stock in WSP", which a storefront does not unblock but a customer list and price editor do. The storefront is next and nothing in this phase presumes it. |
| D-021 | 2026-11-15 | Staff screen | `GET /staff` is read-only for now; people are still created on the WordPress Users screen with one of the six store roles, and a WordPress administrator is reported as the store owner. | WordPress owns user creation, password policy and email. A half-built invite flow would either duplicate that or bypass it. The screen answers the question staff actually ask — who can confirm payments — without inventing a second account system. |
| D-022 | 2026-11-15 | Customer totals | `customers.total_spent_kobo`, `order_count` and `last_order_at` are recomputed from the customer's orders on every order create and status change, instead of being incremented. | Phase 4's customer screen showed ₦0 for every customer because nothing maintained the columns. Recomputing is idempotent, survives cancellations and corrections, and needs no reconciliation job. The write is one indexed `UPDATE ... JOIN` per order change. |
| D-025 | 2026-11-16 | Storefront interactivity | Swatches, photo switching and the URL state are plain JavaScript with progressive enhancement, not the Interactivity API. | Every swatch is still a link the server renders, so the page works without JavaScript, a shared link opens on the chosen value and nothing needs a build step or a block theme. The brief names the Interactivity API (§6.2); the behaviour it describes is delivered, the transport is simpler. Moving to it later is a wrapper around the same markup. |
| D-024 | 2026-11-16 | Storefront theme | The shop ships a PHP-templated theme with block support (`theme/storekeeper-storefront`) instead of a pure block theme. Product pages are engine routes (`/product/{slug}/`) because products live in the engine's tables, not in `wp_posts`; PHP templates let a route render inside the theme's chrome. The product grid also ships as a dynamic block, so a merchant on any block theme can place products on a page. | A block theme's templates cannot currently own a non-post route, and mirroring every product into a post type would duplicate the catalog and break the "one source of truth" rule. Revisit when the product page becomes a block template backed by a query var. |
| D-023 | 2026-11-16 | Back-office look | The back office is its own app shell (dark section rail, light workspace, one type and control scale) and hides the WordPress admin bar, admin menu and footer on this screen only; the rail carries the links back to WordPress and the storefront. | The brief asks for a phone-first product merchants use daily (§11.1, §11.7), and a stock WordPress screen reads as a settings page. Scoping every rule under `.sk-root` and the `storekeeper-app` body class means nothing else in wp-admin changes, and hiding the chrome is reversible CSS, not a rewrite. See `docs/DESIGN.md`. |
| D-011 | 2026-11-15 | Phase 1 boundary | Customer OTP sessions, storefront, POS sync, gateways and notifications are **not** implemented in this phase; their tables and services land in Phases 3–5 as scheduled in §22. | §22.2 defines Phase 1 acceptance as the engine, migrations and REST skeleton; building screens or adapters now would break the phase gate. |
