| D-002 | 2026-11-15 | Engine ↔ WordPress coupling | The engine talks to the database through a narrow `Core\Database\Connection` interface with two implementations: `WpdbConnection` (production, wraps `$wpdb`) and `PdoConnection` (tests, CLI, WP-CLI tooling). | §6.1 requires the engine to be free of HTTP/HTML knowledge so it can be tested directly. | D-037 | 2026-11-17 | Shipping zones and methods | Zones are the ordered list the brief describes, and the first zone whose areas match the address (whole state or one LGA) wins; a zone with **no areas** is the catch-all and is normally sorted last. Methods live in `shipping_methods` and quote `flat`, `weight_band`, `free_over`, `pickup` and `quote_later` exactly as §13.3 defines them; `quote_later` stores a zero fee and flags the order so the page never calls it free. The catch-all-by-empty-areas rule makes "Rest of Nigeria" expressible without listing 774 LGAs. Re-quoting on submit (server-side, from the method config and cart weight) keeps the browser from ever naming a price. |
| D-038 | 2026-11-17 | Parcels and tracking | A shipment is its own state machine (§14.1). Packing commits **that parcel's** reservations and adds its pieces to `order_items.qty_fulfilled_pieces`; a piece is "allocated but not fulfilled" only while its parcel is still `pending`. Dispatching requires a carrier or delivery method; a failed delivery requires a note. Delivering a pay-on-delivery parcel records the cash collected as a real payment. Returning a parcel can restock the goods (`returnStock`) and lowers the fulfilled count; cancelling is only possible before packing, when no stock has moved. Every change writes a `shipment_events` row and fires `storekeeper/shipment/status_changed`; dispatched, ready-for-pickup and delivered queue a customer email. The public page is `/track/{number}/?t={public_token}` and is token-only, the same rule as the order confirmation page. `/order-received/...` shows the same timeline for a signed-in shopper. | The brief requires per-parcel stock and a timeline; tying fulfilment to packing (not delivery) is what makes "packed but not delivered" show as partially fulfilled. Committing only the parcel's lines is what lets one order leave in several parcels without touching another parcel's reservations. The token in the URL is the only thing standing between a guessed order number and its contents, so it is required everywhere. |
| D-039 | 2026-11-18 | POS and offline sync | A device is registered by a manager, receives a `skd_` token once (stored only as SHA-256), and is tied to one location; cashiers sign in with a 4–6 digit PIN hashed with `password_hash` and locked for 15 minutes after five wrong tries. A counter sale is always `OrderService::create(handed_over_now)`, so stock leaves in the same transaction and a sale the shop already made is never refused — an `oversell` alert and a push warning report the shortfall instead. `client_uuid` is the order idempotency key and `batch_uuid` stores the whole push result, so a retried batch or operation is never applied twice. `/sync/pull` sends the catalog, pack units and price table **in full every time** and uses `change_log` only for stock, customer and order deltas; a cursor older than 7 days forces a full resync. Prices quoted offline are honoured, with a `price_changed_offline` note past a 5% difference. Cash-up is per device/cashier/day and expected cash uses the order's `client_created_at`. | §15 requires a device token, a per-cashier PIN, an always-accepted counter sale and a push protocol whose idempotency is client-generated. Sending the full catalog keeps the device correct without a second change-feed implementation for catalog edits the engine does not hook; store catalogs are small enough for v1. Honouring an offline price is §15.3 rule 4, and the note makes a stale price visible to the merchant. The sale is recorded even when it would oversell because the goods have already left the shop; §9.9 turns that into an alert, not a rejection. |
| D-040 | 2026-11-18 | Platform layer scope | Plans carry limits/features JSON, a limit of `0` means uncapped, and `PlanGate::assertCanAdd()` receives the current count from the caller instead of querying store tables itself. Provisioning is a `SiteProvisioner` interface with a WordPress implementation, logs every step in `platform_jobs`, and leaves the tenant `provisioning` if the seed fails. Invoices are recorded and settled by a verified Paystack webhook or by hand; the engine does **not** initiate a Paystack charge or create a Paystack Plan/Subscription. The webhook refuses with `503` when `storekeeper_platform_paystack_secret` is empty. Dunning runs hourly: `past_due` → `read_only` after grace (7 days) → `suspended` 14 days later, and never deletes. | D-041 | 2026-11-18 | POS rate limits and storefront safety buffer | The POS and sync routes share a `Pos\DeviceGuard`: a registered device gets **120 requests per minute** across `/pos/*` and `/sync/*`, and **20 failed token attempts per minute per client IP** are tolerated before a `429 rate_limited` (with `retry_after`, `limit`, `remaining` in the error data). The counter is a fixed window in a `pos_rate_limits` table (one row per bucket) so it is shared by every PHP worker and survives an object-cache flush; expired rows are deleted by the hourly `storekeeper_check_devices` tick. Separately, storefront availability now subtracts `offline_buffer_units` (default 0) from a location whose **active** device has `last_sync_at` older than `device_stale_minutes` (default 10); each such location contributes `max(0, on_hand − reserved − buffer)` and locations without a stale device keep their full level. A revoked device does not hedge availability. | A leaked or brute-forced device token can otherwise push counter sales until someone notices; the per-device budget stops a runaway loop without throttling ordinary pull/push traffic, and counting only *failed* tokens per IP avoids penalising several tablets behind one shop connection. A table was chosen over a transient because the POS is exactly the traffic that must be limited when the object cache is cold, and a fixed window is enough for a security limit. The buffer is the brief's §15.2 rule: while a tablet has not synced, the server cannot know what it sold offline, so the storefront must stop promising those units. Applying it per location (not to the whole sum) keeps stock at locations with a healthy device fully sellable, and clamping at zero stops a buffer from creating negative stock. |
